# Kubernetes

## 1. Czym jest Kubernetes?

**Kubernetes** to platforma typu **open source służąca do automatyzacji wdrażania, skalowania i zarządzania aplikacjami uruchamianymi w kontenerach**.

Kubernetes jest często skracany do:

**K8s**

Nazwa „K8s” pochodzi od tego, że pomiędzy literą **K** i **s** znajduje się 8 liter.

Najprościej można zapamiętać:

**Docker uruchamia kontenery, a Kubernetes zarządza dużą liczbą kontenerów.**

## 2. Do czego służy Kubernetes?

Kubernetes pomaga między innymi w:

- uruchamianiu kontenerów,
- zarządzaniu kontenerami,
- skalowaniu aplikacji,
- automatycznym odtwarzaniu kontenerów,
- zapewnianiu dostępności aplikacji,
- rozdzielaniu ruchu,
- aktualizowaniu aplikacji,
- zarządzaniu konfiguracją,
- zarządzaniu sekretami,
- wdrażaniu mikroserwisów,
- zarządzaniu aplikacjami w chmurze.

Przykładowo:

```text id="9p0m3f"
Aplikacja
   │
   ▼
Kubernetes
   │
   ├── Container 1
   ├── Container 2
   ├── Container 3
   └── Container 4
```

## 3. Kubernetes a Docker

Docker i Kubernetes nie są tym samym.

**Docker** służy między innymi do tworzenia i uruchamiania kontenerów.

**Kubernetes** zarządza kontenerami uruchomionymi w większym środowisku.

Można to zapamiętać:

```text id="6r8z2h"
Docker
→ "Uruchom ten kontener."

Kubernetes
→ "Uruchom 10 instancji tej aplikacji,
   kontroluj ich stan i odtwórz je,
   jeżeli któraś przestanie działać."
```

Współczesny Kubernetes korzysta z **container runtime**, np. `containerd`, zamiast wymagać bezpośrednio Dockera jako runtime.

## 4. Kubernetes Cluster

Podstawą Kubernetes jest **cluster**, czyli klaster.

Klaster składa się z węzłów:

```text id="r2j1h4"
Kubernetes Cluster
│
├── Control Plane
│
├── Worker Node
├── Worker Node
└── Worker Node
```

Control Plane zarządza klastrem.

Worker Nodes wykonują pracę aplikacji.

## 5. Node

**Node** to maszyna, na której Kubernetes może uruchamiać workloady.

Node może być:

- fizycznym serwerem,
- maszyną wirtualną,
- maszyną w chmurze.

Przykładowo:

```text id="z1v9mx"
Cluster
│
├── Node 1
│   └── Pods
│
├── Node 2
│   └── Pods
│
└── Node 3
    └── Pods
```

## 6. Control Plane

**Control Plane** jest odpowiedzialny za zarządzanie klastrem.

Można powiedzieć, że jest to „centrum zarządzania” Kubernetes.

Do najważniejszych komponentów należą:

```text id="5g4y7b"
Control Plane
│
├── kube-apiserver
├── etcd
├── kube-scheduler
└── kube-controller-manager
```

W większych środowiskach mogą występować również inne komponenty.

## 7. kube-apiserver

**kube-apiserver** jest głównym punktem komunikacji z Kubernetes API.

Przykładowo:

```text id="3xj4as"
kubectl
   │
   ▼
kube-apiserver
   │
   ▼
Kubernetes Cluster
```

Kiedy wykonujesz:

```bash id="yq8w2a"
kubectl get pods
```

`kubectl` komunikuje się z API Serverem.

## 8. etcd

**etcd** to rozproszony magazyn klucz-wartość używany przez Kubernetes do przechowywania stanu klastra i danych konfiguracyjnych.

Można go traktować jako ważny magazyn informacji o stanie Kubernetes.

```text id="9uwx3w"
Kubernetes
     │
     ▼
   etcd
     │
     ├── konfiguracja
     ├── stan zasobów
     └── informacje o klastrze
```

## 9. kube-scheduler

**kube-scheduler** decyduje, na którym Node powinien zostać uruchomiony nowy Pod.

Przykładowo:

```text id="2d9x8z"
Pod
 │
 ▼
Scheduler
 │
 ├── Node 1
 ├── Node 2
 └── Node 3
       ↓
    wybrany Node
```

Scheduler bierze pod uwagę między innymi dostępne zasoby i reguły określone przez użytkownika.

## 10. kube-controller-manager

**kube-controller-manager** uruchamia kontrolery odpowiedzialne za utrzymywanie pożądanego stanu klastra.

Przykładowo użytkownik określa:

```yaml id="b8p6gx"
replicas: 3
```

Kubernetes powinien dążyć do tego, aby działały 3 repliki.

Jeżeli jedna przestanie działać, odpowiedni kontroler może doprowadzić do ponownego uruchomienia brakującej repliki.

## 11. Worker Node

Worker Node wykonuje właściwe workloady.

Na Node znajdują się między innymi:

```text id="7k7l7m"
Worker Node
│
├── kubelet
├── kube-proxy
└── Container Runtime
       │
       └── Pods
```

## 12. Pod

**Pod** jest podstawową jednostką uruchamiania workloadów w Kubernetes.

Najczęściej jeden Pod zawiera jeden główny kontener.

```text id="p2t9k8"
Pod
│
└── Container
```

Pod może jednak zawierać wiele kontenerów, które współdzielą określone zasoby.

```text id="w2p7q3"
Pod
│
├── Application Container
└── Sidecar Container
```

## 13. Container

Kontener zawiera aplikację wraz z jej zależnościami potrzebnymi do uruchomienia.

Przykładowo:

```text id="2k2e9p"
Pod
 │
 └── Java Application
```

Kubernetes nie zarządza aplikacją bezpośrednio tak jak system operacyjny.

Zarządza jej kontenerami i zasobami związanymi z ich uruchamianiem.

## 14. Deployment

**Deployment** jest jednym z najważniejszych obiektów Kubernetes.

Służy między innymi do deklaratywnego zarządzania aplikacją uruchamianą w Podach.

Przykładowo:

```yaml id="8i7h2b"
apiVersion: apps/v1
kind: Deployment

spec:
  replicas: 3
```

Oznacza to, że chcemy mieć **3 repliki** aplikacji.

Schemat:

```text id="z2f6d4"
Deployment
    │
    ├── Pod
    ├── Pod
    └── Pod
```

## 15. ReplicaSet

**ReplicaSet** zapewnia określoną liczbę Podów.

Deployment zazwyczaj zarządza ReplicaSetem.

```text id="b1r8e0"
Deployment
     │
     ▼
 ReplicaSet
     │
 ┌───┼───┐
 ▼   ▼   ▼
Pod Pod Pod
```

Dlatego w praktyce najczęściej tworzysz **Deployment**, a Kubernetes zajmuje się ReplicaSetem.

## 16. Service

Pody są zasobami dynamicznymi.

Ich adresy IP mogą się zmieniać.

Dlatego Kubernetes posiada obiekt **Service**.

Service zapewnia stabilny sposób dostępu do grupy Podów.

```text id="p8a0b7"
              Service
                 │
        ┌────────┼────────┐
        ▼        ▼        ▼
      Pod 1    Pod 2    Pod 3
```

## 17. Service Types

Najważniejsze typy Service to:

**ClusterIP**

**NodePort**

**LoadBalancer**

### ClusterIP

Domyślny typ.

Service jest dostępny wewnątrz klastra.

```text id="d4d7r0"
Service
   │
   ├── Pod
   ├── Pod
   └── Pod
```

### NodePort

Udostępnia Service poprzez port na Node.

### LoadBalancer

Pozwala wystawić usługę za pomocą load balancera, szczególnie w środowiskach chmurowych.

## 18. Namespace

**Namespace** pozwala logicznie podzielić zasoby klastra.

Przykładowo:

```text id="f4s7j0"
Cluster
│
├── development
│   ├── Pods
│   └── Services
│
├── testing
│   ├── Pods
│   └── Services
│
└── production
    ├── Pods
    └── Services
```

Jest to bardzo przydatne w większych środowiskach.

## 19. ConfigMap

**ConfigMap** służy do przechowywania konfiguracji, która nie jest tajna.

Przykładowo:

```text id="v6r5e1"
DATABASE_HOST=db
DATABASE_PORT=5432
APP_MODE=production
```

Aplikacja może pobierać te wartości z ConfigMap.

## 20. Secret

**Secret** służy do przechowywania danych wrażliwych, takich jak:

- hasła,
- tokeny,
- klucze,
- dane uwierzytelniające.

Przykładowo:

```text id="q5u8a2"
Secret
│
├── DB_USERNAME
├── DB_PASSWORD
└── API_TOKEN
```

Warto pamiętać, że Kubernetes Secret nie powinien być automatycznie utożsamiany z pełnym szyfrowaniem danych — bezpieczeństwo sekretów zależy również od konfiguracji klastra i sposobu ich przechowywania.

## 21. Volume

Kontenery mają własny system plików, którego cykl życia może być związany z kontenerem.

Kubernetes udostępnia mechanizmy **Volume**, aby zapewnić przechowywanie danych poza cyklem życia konkretnego kontenera.

Przykładowo:

```text id="f5e4f8"
Pod
 │
 ▼
Volume
 │
 ▼
Persistent Storage
```

## 22. PersistentVolume

**PersistentVolume (PV)** reprezentuje zasób pamięci masowej dostępny dla klastra.

Przykładowo:

```text id="e4s7g1"
PersistentVolume
       │
       ▼
Storage
```

## 23. PersistentVolumeClaim

**PersistentVolumeClaim (PVC)** jest żądaniem wykorzystania odpowiedniej przestrzeni dyskowej.

Schemat:

```text id="t7n6x2"
Pod
 │
 ▼
PVC
 │
 ▼
PV
 │
 ▼
Storage
```

Można zapamiętać:

**PV = dostępny zasób**

**PVC = żądanie wykorzystania zasobu**

## 24. Ingress

**Ingress** umożliwia zarządzanie dostępem HTTP/HTTPS do usług znajdujących się w klastrze.

Przykładowo:

```text id="e2v5s1"
Internet
   │
   ▼
Ingress
   │
   ├── /api/users → User Service
   ├── /api/orders → Order Service
   └── /api/products → Product Service
```

Ingress może wykonywać między innymi routing ruchu na podstawie domeny lub ścieżki.

Współczesne klastry mogą również korzystać z **Gateway API** jako bardziej rozbudowanego mechanizmu zarządzania ruchem.

## 25. kubelet

**kubelet** działa na każdym Worker Node.

Odpowiada między innymi za zapewnienie, że kontenery opisane przez PodSpec są uruchomione i działają zgodnie z oczekiwaniami.

```text id="5z5z7s"
Worker Node
│
├── kubelet
│
└── Pods
```

## 26. kube-proxy

**kube-proxy** jest komponentem odpowiedzialnym za część funkcji związanych z obsługą ruchu sieciowego dla Service.

Warto jednak wiedzieć, że współczesne implementacje Kubernetes mogą realizować część tych funkcji również za pomocą innych mechanizmów sieciowych.

## 27. Container Runtime

Kubernetes potrzebuje **container runtime**, czyli komponentu odpowiedzialnego za uruchamianie kontenerów.

Przykładem jest:

**containerd**

Innym przykładem jest **CRI-O**.

Kubernetes komunikuje się z runtime poprzez **CRI — Container Runtime Interface**.

## 28. kubectl

**kubectl** to podstawowe narzędzie wiersza poleceń do komunikacji z Kubernetes.

Przykładowo:

```bash id="52e3t5"
kubectl get nodes
```

pokazuje Node'y.

```bash id="j0n4k4"
kubectl get pods
```

pokazuje Pody.

```bash id="y6m7m0"
kubectl get services
```

pokazuje Service.

```bash id="6zv3cw"
kubectl get deployments
```

pokazuje Deploymenty.

## 29. Tworzenie Deploymentu

Możemy opisać aplikację w pliku YAML.

Przykład:

```yaml id="8hbr9s"
apiVersion: apps/v1
kind: Deployment
metadata:
  name: my-app

spec:
  replicas: 3
  selector:
    matchLabels:
      app: my-app

  template:
    metadata:
      labels:
        app: my-app

    spec:
      containers:
        - name: my-app
          image: nginx
```

Następnie:

```bash id="w7g8q7"
kubectl apply -f deployment.yaml
```

Kubernetes odczyta deklarację i będzie dążył do jej realizacji.

## 30. Deklaratywność

Jedną z najważniejszych idei Kubernetes jest **declarative configuration**.

Zamiast mówić:

> Uruchom teraz kontener A, potem B, potem C.

opisujemy:

> Chcę mieć trzy repliki aplikacji A.

Kubernetes sam stara się doprowadzić system do takiego stanu.

```text id="0r5k2j"
Desired State
      │
      ▼
Kubernetes
      │
      ▼
Actual State
```

Kubernetes stale porównuje stan rzeczywisty z pożądanym i podejmuje działania korygujące.

## 31. Self-Healing

Kubernetes posiada mechanizmy **self-healing**.

Jeżeli Pod przestanie działać, Kubernetes może uruchomić nowy.

```text id="5l9g0e"
Pod 1
  │
  X
Crash
  │
  ▼
Kubernetes
  │
  ▼
New Pod
```

Dzięki temu aplikacja może automatycznie odzyskać działanie.

## 32. Skalowanie

Kubernetes pozwala zwiększać liczbę replik aplikacji.

Przykładowo:

```bash id="x8a8pl"
kubectl scale deployment my-app --replicas=5
```

Możemy przejść z:

```text id="7x0l6g"
2 Pody
```

do:

```text id="3y1v7n"
5 Podów
```

## 33. Horizontal Pod Autoscaler

**HPA — Horizontal Pod Autoscaler** może automatycznie zmieniać liczbę replik w zależności od określonych metryk.

Przykładowo:

```text id="f4v4eq"
CPU ↑
 │
 ▼
HPA
 │
 ▼
więcej Podów
```

Kiedy obciążenie spada:

```text id="g3t3q1"
CPU ↓
 │
 ▼
HPA
 │
 ▼
mniej Podów
```

## 34. Rolling Update

Kubernetes może aktualizować aplikację stopniowo.

Przykładowo mamy:

```text id="k1c4xe"
Version 1
Pod 1
Pod 2
Pod 3
```

Chcemy przejść do:

```text id="e0m2qb"
Version 2
Pod 1
Pod 2
Pod 3
```

Kubernetes może stopniowo wymieniać stare Pody na nowe.

Jest to **Rolling Update**.

## 35. Rollback

Jeżeli nowa wersja aplikacji powoduje problemy, Deployment może zostać cofnięty do wcześniejszej wersji.

Przykładowo:

```bash id="0i8g4n"
kubectl rollout undo deployment my-app
```

## 36. Health Checks

Kubernetes może sprawdzać stan aplikacji za pomocą probe'ów.

Najważniejsze:

**Liveness Probe**

**Readiness Probe**

**Startup Probe**

### Liveness Probe

Sprawdza, czy kontener nadal działa poprawnie.

### Readiness Probe

Sprawdza, czy aplikacja jest gotowa do przyjmowania ruchu.

### Startup Probe

Pomaga obsługiwać aplikacje, które potrzebują dużo czasu na uruchomienie.

## 37. Labels

**Labels** to etykiety przypisywane zasobom.

Przykład:

```yaml id="6spnzw"
labels:
  app: backend
  environment: production
```

Labels są wykorzystywane między innymi do organizowania i wybierania zasobów.

## 38. Selectors

**Selectors** pozwalają wybierać zasoby posiadające określone labels.

Przykładowo Service może wskazywać:

```yaml id="5xsh1h"
selector:
  app: backend
```

Wtedy Service kieruje ruch do Podów oznaczonych:

```text id="q9kq6y"
app=backend
```

## 39. Kubernetes i mikroserwisy

Kubernetes bardzo dobrze pasuje do architektury mikroserwisowej.

Przykładowo:

```text id="v5e4o6"
Kubernetes
│
├── User Service
│   ├── Pod
│   └── Pod
│
├── Order Service
│   ├── Pod
│   └── Pod
│
├── Payment Service
│   ├── Pod
│   └── Pod
│
└── Notification Service
    ├── Pod
    └── Pod
```

Każdy mikroserwis może mieć własny Deployment i Service.

## 40. Kubernetes i Cloud

Kubernetes jest bardzo często wykorzystywany w chmurze.

Popularne zarządzane usługi Kubernetes obejmują:

**Amazon EKS**

**Azure AKS**

**Google Kubernetes Engine (GKE)**

Dzięki usługom zarządzanym dostawca chmury może przejąć część obowiązków związanych z zarządzaniem Control Plane.

## 41. Kubernetes lokalnie

Kubernetes można uruchomić lokalnie.

Popularne rozwiązania to:

**Minikube**

**kind**

**Docker Desktop Kubernetes**

Można dzięki nim stworzyć środowisko do nauki bez potrzeby posiadania dużego klastra produkcyjnego.

Trzeba zrozumieć między innymi:

- Pods,
- Deployments,
- Services,
- Networking,
- Storage,
- ConfigMaps,
- Secrets,
- Namespaces,
- Ingress,
- RBAC,
- Helm,

- bezpieczeństwo klastra.

Dla jednej prostej aplikacji Kubernetes może być przesadą.

**Control Plane** → komponenty zarządzające klastrem.

**Node** → maszyna należąca do klastra.

**Worker Node** → Node wykonujący workloady.

**Pod** → podstawowa jednostka uruchamiania workloadów.

**Container** → kontener z aplikacją.

**Deployment** → deklaratywne zarządzanie aplikacją i jej replikami.

**ReplicaSet** → utrzymuje określoną liczbę Podów.

**Service** → stabilny dostęp do grupy Podów.

**Ingress** → routing HTTP/HTTPS do usług.

**Namespace** → logiczne wydzielenie zasobów.

**ConfigMap** → konfiguracja niesekretna.

**Secret** → dane wrażliwe.

**Volume** → mechanizm udostępniania pamięci dla Podów.

**PV** → PersistentVolume, zasób storage.

**PVC** → PersistentVolumeClaim, żądanie storage.

**kubectl** → narzędzie CLI do zarządzania Kubernetes.

**etcd** → magazyn stanu klastra.

**Scheduler** → wybiera Node dla nowych Podów.

**HPA** → automatyczne skalowanie liczby Podów.

**Rolling Update** → stopniowe wdrażanie nowej wersji.

**Rollback** → cofnięcie wdrożenia.

**Liveness Probe** → sprawdza, czy aplikacja nadal działa.

**Readiness Probe** → sprawdza, czy aplikacja jest gotowa przyjmować ruch.

## 47. Kubernetes w jednym zdaniu

**Kubernetes to otwartoźródłowa platforma do automatyzacji wdrażania, skalowania, aktualizowania i zarządzania aplikacjami uruchamianymi w kontenerach, szczególnie popularna w środowiskach mikroserwisowych i chmurowych.**
